# Document Collections

This file explains every document collection in DeskMind's ArangoDB database. Each section covers:
- **What it is** — simple explanation
- **Why it exists** — what problem it solves
- **Real-world analogy** — so you can relate to it
- **Fields** — every field explained with an example
- **Example document** — a complete real-looking document

---

## 1. `tickets`

### What it is
Every support ticket submitted to DeskMind. This is the most important collection — everything else exists to help classify and route these tickets.

### Why it exists
Without tickets, there's nothing to route. This collection stores the ticket text, the AI's classification, confidence score, and the vector embedding used for similarity search.

### Real-world analogy
Think of it as a help desk inbox. Each ticket is like an email from someone reporting a problem.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string (auto) | `"12345"` | Unique ID generated automatically by ArangoDB. Every ticket needs a unique identifier. |
| `title` | string | `"PostgreSQL not accepting connections"` | Short one-line summary. This is what appears in the ticket list. Users scan titles to find their ticket. |
| `description` | string | `"prod-db-01 refusing connections since 10am. max_connections reached at 100. App team reporting 502 errors on the checkout page."` | Detailed problem description. This is the main text the AI reads to classify the ticket. More detail = better classification. |
| `category` | string | `"Database"` | One of 6 values: `Infrastructure`, `Application`, `Security`, `Database`, `Storage`, `Network`. This is the AI's classification — it determines which team gets the ticket. |
| `priority` | string | `"high"` | One of 4 values: `critical`, `high`, `medium`, `low`. Also assigned by AI. Determines how fast the team must respond (SLA). |
| `status` | string | `"routed"` | Ticket lifecycle: `open` (just submitted) → `routed` (AI sent to team) or `escalated` (AI not confident, needs human) → `in_progress` (team working) → `resolved` (fixed) → `closed` (confirmed). |
| `confidence_score` | float | `0.92` | How sure the AI is about its classification (0.0 to 1.0). If below 0.70 (configurable), the ticket is escalated to a human instead of auto-routed. |
| `ai_reasoning` | string | `"PostgreSQL connection issue on production database server. Mentions max_connections limit and prod-db-01."` | The AI explains why it chose that category. Helps humans review escalated tickets and debug misclassifications. |
| `submitted_by` | string | `"john.doe@company.com"` | Who reported the issue. For tracking and follow-up. |
| `embedding` | array[384] | `[0.012, -0.034, 0.089, ...]` | A list of 384 numbers that represent the **meaning** of the ticket description. Generated by the MiniLM AI model. Used to find similar past tickets — two tickets with similar meanings will have similar embeddings, even if they use different words. |
| `created_at` | datetime | `"2026-04-20T10:00:00Z"` | When the ticket was submitted. Used for SLA tracking — if created_at + sla_hours passes without resolution, trigger an alert. |
| `resolved_at` | datetime/null | `null` or `"2026-04-20T12:30:00Z"` | When the ticket was fixed. `resolved_at - created_at` = how long it took to fix. Null if not yet resolved. |
| `quality_score` | string | `"HIGH"` | Input quality assessment: `HIGH` (detailed, has entities), `MEDIUM` (some detail), `LOW` (vague, short). LOW quality tickets have confidence capped — prevents confident wrong answers on bad input. |
| `secondary_category` | string/null | `"Database"` or `null` | For ambiguous tickets that touch 2 domains. E.g., "Firewall blocking database port" → primary: Network, secondary: Database. Secondary team gets notified. Null if clearly one category. |
| `classifier_votes` | object/null | `{"llm": {"category": "Database", "confidence": 0.94}, "knn": {...}, "centroid": {...}, "keyword": {...}}` | What each of the 4 independent classifiers decided. Used for debugging misclassifications, tracking which classifier is wrong most often, and explaining decisions to users. Null for historical/seed tickets. |

## 2. `teams`

### What it is
The 6 IT teams that handle support tickets. Each team specializes in one domain.

### Why it exists
When the AI classifies a ticket as "Database", the system needs to know: which team handles Database tickets? What's their SLA? Who should be alerted if they're too slow? The teams collection answers all of this.

### Real-world analogy
Think of departments in a hospital. The ER handles emergencies, cardiology handles heart issues, neurology handles brain issues. Each department has its own staff and response times.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"db-admin"` | Short slug used as the team ID. Referenced by routing rules and edges. Using readable slugs (not auto-generated IDs) makes debugging easier. |
| `name` | string | `"Database Admin"` | Full display name shown in the UI. |
| `domain` | string | `"Database"` | Maps directly to ticket categories. When ticket.category = "Database", we find the team where domain = "Database". |
| `escalation_contact` | string | `"db-lead@company.com"` | Email to alert when SLA is about to breach. The system sends a notification: "Ticket #12345 (high priority) assigned to your team has been open for 3.5 hours. SLA is 4 hours." |
| `sla_hours` | object | `{"critical": 2, "high": 4, "medium": 8, "low": 24}` | Response time targets per priority. Critical = 2 hour response, Low = 24 hour response. These numbers drive the alert system. |

### Example document

```json
{
  "_key": "db-admin",
  "name": "Database Admin",
  "domain": "Database",
  "escalation_contact": "db-lead@company.com",
  "sla_hours": {
    "critical": 2,
    "high": 4,
    "medium": 8,
    "low": 24
  }
}
```

### All 6 teams

| _key | name | domain |
|------|------|--------|
| `infra-ops` | Infrastructure Ops | Infrastructure |
| `app-support` | Application Support | Application |
| `security-ops` | Security Ops | Security |
| `db-admin` | Database Admin | Database |
| `storage-ops` | Storage Ops | Storage |
| `network-eng` | Network Engineering | Network |

## 3. `engineers`

### What it is
Individual team members with their skills and expertise.

### Why it exists
When the AI routes a ticket, it can go further than just "send to Database Admin team". It can say: "Alex Chen on the Database Admin team has PostgreSQL expertise and resolved a similar issue on prod-db-01 last month." This level of detail comes from the engineers collection + graph traversal.

### Real-world analogy
A company directory that lists not just names, but what each person specializes in.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string (auto) | `"98765"` | Unique ID for each engineer. |
| `name` | string | `"Alex Chen"` | Engineer's full name. Displayed when the system recommends a specific person. |
| `role` | string | `"Senior DBA"` | Job title. Helps match expertise level to ticket severity — senior engineers for critical issues. |
| `expertise` | array | `["PostgreSQL", "Redis", "backup-recovery"]` | List of technologies they know. When a PostgreSQL ticket comes in, graph traversal finds engineers with "PostgreSQL" in their expertise. |
| `email` | string | `"alex.chen@company.com"` | Contact information for assignment notifications. |

### Example document

```json
{
```

## 4. `servers`

### What it is
Physical or virtual machines in the company's infrastructure.

### Why it exists
Users often mention server names in tickets: "prod-db-01 is down". The AI needs to know what prod-db-01 is — is it a database server? Where is it located? What services run on it? Who manages it? All of this context helps the AI classify and route more accurately.

### Real-world analogy
A building directory in a hospital. "Room 301" isn't just a room number — it's the MRI suite, on the 3rd floor, managed by Radiology department, with a GE MRI machine inside.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"prod-db-01"` | Server hostname. This is what users type in tickets, so using hostname as the key makes it easy to look up directly. |
| `ip` | string | `"10.0.1.10"` | IP address. Sometimes tickets mention IPs instead of hostnames. The system can match either way. |
| `type` | string | `"database"` | Server category: `database`, `application`, `web`, `monitoring`, `auth`, `storage`. Helps AI confirm its classification — if a ticket mentions a "database" type server, it's likely a Database category ticket. |
| `datacenter` | string | `"dc-east-1"` | Physical location. If 3 tickets come from servers in the same datacenter within 10 minutes, it might be a datacenter-wide issue, not individual server problems. |
| `os` | string | `"Ubuntu 22.04"` | Operating system. Relevant for OS-specific troubleshooting — a Linux fix won't work on Windows. |
| `cpu` | number | `8` | Number of CPU cores. Context for performance issues — "CPU at 100%" on a 2-core server is different from an 8-core server. |
| `ram_gb` | number | `32` | Memory in gigabytes. If a server has 4GB RAM and the ticket says "out of memory", the AI can suggest scaling up. |

### Example document

```json
{
  "_key": "prod-db-01",
  "ip": "10.0.1.10",
  "type": "database",
  "datacenter": "dc-east-1",
  "os": "Ubuntu 22.04",
  "cpu": 8,
  "ram_gb": 32
}
```

## 5. `services`

### What it is
Software services running on servers — databases, web servers, APIs, monitoring tools.

### Why it exists
A server is just hardware. The important thing is what **software** runs on it. When someone says "PostgreSQL is slow", the AI needs to know: which servers run PostgreSQL? What other services depend on it? This is how the AI finds the root cause — not just the symptom.

### Real-world analogy
If servers are buildings, services are the businesses inside them. "The bakery is closed" → which building is the bakery in? → who owns that building? → are other businesses in the same building also affected?

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"postgresql"` | Short service ID. Used in edges to connect to servers. |
| `name` | string | `"PostgreSQL"` | Full display name. |
| `version` | string | `"15.4"` | Software version. Important because some bugs are version-specific — "upgrade from 15.4 to 15.5 to fix the replication bug." |
| `port` | number | `5432` | Network port. When a ticket mentions "port 5432 connection refused", the system maps port 5432 → PostgreSQL automatically. |
| `protocol` | string | `"tcp"` | Connection protocol (tcp, http, grpc). Helps the AI understand what type of connection issue it is. |

### Example document

```json
{
  "_key": "postgresql",
  "name": "PostgreSQL",
  "version": "15.4",
  "port": 5432,
  "protocol": "tcp"
}
```

## 6. `network_devices`

### What it is
Network infrastructure — firewalls, switches, routers, load balancers.

### Why it exists
Network devices are the invisible layer between servers. When "prod-db-01 is unreachable", it might not be the server's fault — a firewall might be blocking traffic, or a switch might have failed. Without this collection, the AI can't investigate network-layer causes.

### Real-world analogy
Roads and traffic lights between buildings. If you can't reach the hospital, maybe the road is closed (switch down) or there's a roadblock (firewall rule).

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"fw-prod-01"` | Device hostname. |
| `type` | string | `"firewall"` | Device type: `firewall`, `switch`, `router`, `load_balancer`. Determines what kind of network investigation to do. |
| `ip` | string | `"10.0.0.1"` | Management IP address. |
| `model` | string | `"Palo Alto PA-3260"` | Hardware model. Some issues are model-specific. |

### Example document

```json
{
  "_key": "fw-prod-01",
  "type": "firewall",
  "ip": "10.0.0.1",
  "model": "Palo Alto PA-3260"
}
```

## 7. `error_codes`

### What it is
A catalog of known error patterns that appear in tickets.

### Why it exists
Users often paste error messages: "Getting FATAL: too many connections." Instead of the AI having to figure out what this error means every time, we pre-define known errors with their severity and associated service. This makes classification faster and more accurate.

### Real-world analogy
A medical symptom database. When a patient says "chest pain on the left side", the doctor doesn't start from scratch — they look up known conditions associated with that symptom.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"ERR-PG-001"` | Unique error ID. Prefixed by service for readability. |
| `pattern` | string | `"FATAL: too many connections"` | The actual error text to match against ticket descriptions. System checks if the ticket text contains this pattern. |
| `service` | string | `"postgresql"` | Which service produces this error. Links to the services collection for graph traversal. |
| `severity` | string | `"high"` | Pre-defined severity. Some errors are always critical (data corruption), some always low (cosmetic warning). |

### Example document

```json
{
  "_key": "ERR-PG-001",
  "pattern": "FATAL: too many connections",
  "service": "postgresql",
  "severity": "high"
}
```

## 8. `runbooks`

### What it is
Pre-written guides for handling common IT issues. Step-by-step procedures that any engineer can follow.

### Why it exists
When the AI routes a ticket, it can also say: "Here's the documented procedure for this type of issue." This helps engineers resolve tickets faster — they don't have to figure out the steps from scratch. It also ensures consistency — everyone follows the same proven procedure.

### Real-world analogy
Recipe cards in a kitchen. When an order comes in for pasta, the chef doesn't invent a new recipe each time — they follow the documented recipe.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"KB-0001"` | Knowledge base ID. KB prefix for readability. |
| `title` | string | `"PostgreSQL connection limit exceeded"` | What problem this runbook solves. Searchable by both humans and AI. |
| `steps` | array | `["Check connections with pg_stat_activity", "Kill idle connections", "Increase max_connections", "Restart PostgreSQL"]` | Step-by-step fix instructions. Must be specific enough that any team member can follow them. |
| `category` | string | `"Database"` | Which domain this runbook belongs to. For filtering. |
| `embedding` | array[384] | `[0.023, -0.011, ...]` | Vector representation of the runbook content. Used for AI similarity search — "find the runbook most relevant to this ticket." |

### Example document

```json
{
  "_key": "KB-0001",
  "title": "PostgreSQL connection limit exceeded",
  "steps": [
    "Check current connections: SELECT count(*) FROM pg_stat_activity;",
    "Identify idle connections: SELECT * FROM pg_stat_activity WHERE state = 'idle';",
    "Kill idle connections if needed: SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle';",
    "Increase max_connections in postgresql.conf if needed",
    "Restart PostgreSQL: sudo systemctl restart postgresql"
  ],
  "category": "Database",
  "embedding": [0.023, -0.011, "... 382 more numbers ..."]
}
```

## 9. `resolutions`

### What it is
Records of actual fixes applied to specific tickets. Different from runbooks — runbooks are generic guides, resolutions are specific actions taken on a real ticket.

### Why it exists
This is how DeskMind **learns over time**. Every time a ticket is resolved, a resolution is recorded. When a new similar ticket comes in, the AI searches for similar past resolutions. If a resolution had high effectiveness, it's recommended first.

### Real-world analogy
A doctor's case notes. "Patient #123 had chest pain, we did X-ray and found Y, treated with Z, patient recovered." A runbook says "how to handle chest pain in general." A resolution says "what we did for this specific patient."

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string (auto) | `"54321"` | Unique resolution ID. |
| `steps` | array | `["Checked max_connections was 100", "Increased to 200 in postgresql.conf", "Restarted PostgreSQL", "Verified with pg_isready"]` | The actual commands/actions taken. Specific to this ticket, not generic. |
| `effectiveness` | float | `0.95` | How well this fix worked (0.0 to 1.0). Starts at 1.0 when first resolved. Drops if the issue recurs (0.5) or ticket reopens (0.3). AI prefers higher effectiveness resolutions. |
| `embedding` | array[384] | `[0.019, -0.042, ...]` | Vector of the resolution text. Used to find similar past fixes when a new ticket comes in. |

### Example document

```json
{
  "_key": "54321",
  "steps": [
    "Checked max_connections was set to 100",
    "Increased max_connections to 200 in postgresql.conf",
    "Restarted PostgreSQL with: sudo systemctl restart postgresql",
    "Verified connections restored with: pg_isready -h localhost"
  ],
  "effectiveness": 0.95,
  "embedding": [0.019, -0.042, "... 382 more numbers ..."]
}
```

## 10. `routing_rules`

### What it is
A rules table that maps ticket categories and priorities to teams. This is the lookup table the system uses after AI classification.

### Why it exists
When the AI says "this is a Database ticket with high priority", the system needs to know: which team handles that combination? Routing rules answer this question. Having rules in a collection (instead of hardcoded) means you can change routing without changing code — just update the rules.

### Real-world analogy
A phone directory: "For billing, press 1. For technical support, press 2. For emergencies, press 9." The mapping from department to extension number is the routing rule.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string (auto) | `"67890"` | Unique rule ID. |
| `category` | string | `"Database"` | Matches the ticket's category. |
| `priority` | string | `"high"` | Matches the ticket's priority. Allows different routing for different severities (e.g., critical tickets to a senior team). |
| `target_team` | string | `"db-admin"` | Which team `_key` to route to. References the teams collection. |
| `is_active` | boolean | `true` | Toggle rules on/off without deleting. Useful during team changes. |

### Example document

```json
{
  "_key": "67890",
  "category": "Database",
  "priority": "high",
  "target_team": "db-admin",
  "is_active": true
}
```

### Default rules (24 total)

For each of the 6 categories, there are 4 rules (one per priority level). All currently route to the same team regardless of priority:

| Category | critical | high | medium | low |
|----------|----------|------|--------|-----|
| Infrastructure | infra-ops | infra-ops | infra-ops | infra-ops |
| Application | app-support | app-support | app-support | app-support |
| Security | security-ops | security-ops | security-ops | security-ops |
| Database | db-admin | db-admin | db-admin | db-admin |

## 11. `audit_log`

### What it is
A log of every action taken on every ticket — by AI or by humans. Think of it as a security camera recording for your ticket system.

### Why it exists
When the AI classifies a ticket, you need to know: what did it decide? Why? How confident was it? And if a human overrides the AI's decision, you need a record of that too. Without audit_log, you have no visibility into what happened to a ticket between submission and resolution.

### Real-world analogy
A patient's medical chart. Every doctor visit, every test, every prescription is recorded with the date, who did it, and why. If something goes wrong, you can trace back exactly what happened.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string (auto) | `"99001"` | Unique log entry ID. |
| `ticket_id` | string | `"12345"` | Which ticket this action is about. Indexed for fast lookup: "show me everything that happened to ticket #12345." |
| `action` | string | `"classified"` | What happened: `classified` (AI assigned category), `routed` (sent to team), `escalated` (AI not confident), `overridden` (human changed AI's decision), `resolved` (ticket fixed), `cache_hit` (used cached result), `fallback_triggered` (AI failed, used backup method). |
| `actor` | string | `"ai-phi3"` or `"alex.chen@company.com"` | Who did it — an AI model name or a human's email. Helps distinguish: "the AI classified it, then a human overrode it." |
| `old_value` | object | `{"category": "Network"}` | What it was before. Only for changes — if the AI classified as Network but a human changed it to Database, old_value = Network. |
| `new_value` | object | `{"category": "Database"}` | What it became after the action. |
| `confidence_score` | float | `0.62` | AI's confidence at that moment. Especially useful for escalations — "the AI was only 62% sure, so it escalated." |
| `confidence_signals` | object | `{"logprob": -1.2, "centroid_sim": 0.78, "knn_agreement": 0.6}` | Detailed breakdown of how the AI calculated its confidence. For debugging and improving the AI model. |
| `reasoning` | string | `"Ticket mentions VPN but root cause is firewall rule change"` | Human-readable explanation of why this action was taken. |
| `created_at` | datetime | `"2026-04-23T10:05:00Z"` | When the action happened. Indexed for time-ordered queries. |

### Example document — AI classifies a ticket

```json
{
  "_key": "99001",
  "ticket_id": "12345",
  "action": "classified",
  "actor": "ai-phi3",
  "old_value": null,
  "new_value": {
    "category": "Database",
    "priority": "high"
  },
  "confidence_score": 0.92,
  "confidence_signals": {
    "logprob": -0.8,
    "centroid_sim": 0.91,
    "knn_agreement": 0.88
  },
  "reasoning": "PostgreSQL connection issue on production database server. Mentions max_connections limit.",
  "created_at": "2026-04-23T10:00:05Z"
}
```

### Example document — Human overrides AI decision

```json
{
  "_key": "99002",
  "ticket_id": "12345",
  "action": "overridden",
  "actor": "alex.chen@company.com",
```

### Example query — Show full history of a ticket

```aql
FOR log IN audit_log
  FILTER log.ticket_id == "12345"
  SORT log.created_at ASC
  RETURN {
    time: log.created_at,
    action: log.action,
    by: log.actor,
    details: log.new_value,
    confidence: log.confidence_score
  }
```

**Result:**
```json
[
```

## 12. `category_centroids`

### What it is
Stores the **average embedding** (centroid) for each of the 6 ticket categories. Used by the centroid classifier to determine which category a new ticket is closest to.

### Why it exists
Instead of comparing a new ticket to every past ticket individually, we compare it to 6 centroids — one per category. This is like asking "which group's center am I closest to?" It's fast and robust, even when no single past ticket is very similar.

### Real-world analogy
In a school, each grade has a classroom. The centroid is like the **center of each classroom**. When a new student arrives, you check which classroom center they're closest to — that's their grade.

### Fields

| Field | Type | Example | Why it exists |
|-------|------|---------|---------------|
| `_key` | string | `"database"` | Category ID (lowercase). One per category. |
| `category` | string | `"Database"` | Display name of the category. |
| `embedding` | array[384]/null | `[0.77, -0.12, 0.29, ...]` | The average embedding of all tickets in this category. Null until computed by seed_db.py. |
| `ticket_count` | number | `42` | How many tickets were used to compute this centroid. More tickets = more reliable centroid. |
| `last_updated` | datetime/null | `"2026-04-24T10:00:00Z"` | When the centroid was last recomputed. Centroids should be refreshed periodically as new tickets are added. |

### Example document

```json
{
  "_key": "database",
  "category": "Database",
  "embedding": [0.77, -0.12, 0.29, 0.05, -0.38, "... 379 more numbers"],
  "ticket_count": 42,
  "last_updated": "2026-04-24T10:00:00Z"
}
```
